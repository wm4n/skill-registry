# 產品管理 Agent（PM Bot）設計文件

日期：2026-07-15
狀態：設計已確認，待實作規劃

## 背景與目標

現有一個遊戲產品（未來會有更多產品），開發流程已高度 bot 化，跑在 openab（Docker）上、透過 Discord mention 協調：

```
人類發想 → 人類開 GitHub issue → bot 需求分析 → bot 開發 → bot review/建 PR
→ 人類 merge → 人類測試 → 人類發佈（Play Console / App Store Connect）
```

本設計新增一個**產品管理 agent（PM bot）**，接手最上游「發想與開 issue」的角色，並負責產品健康度觀測，目標是：

1. **成長產品**：以數據驅動的假設實驗迴圈持續改善產品
2. **誠實判斷終止**：當產品觸及預先承諾的終止條件時，備齊決策材料建議人類終止

最終（分階段）接手目前所有人類環節：發想、開 issue、成長分析、merge、測試、發佈。

## 定位與角色

- PM bot 是 **openab 上的一個新 bot**，與現有 bot 平行部署，透過 Discord mention 溝通。openab 的訊息權限設定讓它可 mention 需求分析 bot（pipeline 入口）與人類。
- **建議制（advisory-first）**：日常操作自主，重大決策提案後執行，生死決策永遠只建議（見「決策權限」）。
- **PM bot 不做開發工作**：只產出「意圖與方向」層級的 issue，細節規格交給現有需求分析 bot，維持既有 pipeline 分工。
- **多產品擴充**：一個產品一個產品日誌 repo，PM bot 的 config 指向哪個 journal 就管哪個產品。

## 每日循環

由 **openab 內建排程（usercron，`cronjob.toml`）** 觸發。選 usercron 而非 `[[cron.jobs]]`（config.toml）的原因：熱重載（每分鐘偵測 mtime），PM bot 未來可自行調整節奏（如發佈日改為每天兩次檢查）而不需重啟容器。

循環五步驟：

1. **蒐集（Collect）**：依「訊號來源註冊表」（見下節）拉取所有已啟用來源 —— 量化數據、質化回饋、開發狀態。
2. **分析（Analyze）**：與產品日誌的歷史快照比對趨勢 —— 什麼在變好/變差、上次發佈是否反映在數據上。
3. **決定（Decide）**：產出今日行動清單並排優先序。行動類型：開新 issue、調整既有 issue 優先序、對人類發提案、或「今天不需要動作」（合法輸出，不硬找事做）。**含數據缺口偵測（見下節）。**
4. **執行（Act）**：開 GitHub issue（掛 PM bot 標籤）、mention 需求分析 bot 啟動 pipeline、在 Discord 發提案。
5. **回報（Report）**：Discord 日報 —— 數據摘要、今日行動、理由、等待人類事項；全部寫入產品日誌。

## 訊號來源註冊表

PM bot 觀測的不只是量化數據。所有觀測來源登記在產品日誌的 `SOURCES.md`（訊號來源註冊表），分三類：

1. **量化數據**：商店後台（Google Play Developer Reporting API / App Store Connect API：下載、崩潰、評分）、遊戲內分析（接入後：DAU、留存、事件）。
2. **質化回饋**：商店評論（Google Play Reviews API / App Store Connect API）、玩家 issue 回報管道（遊戲內回報、Discord 回報頻道等）、論壇與社群討論（Reddit、巴哈姆特、Discord 社群伺服器等）。
3. **開發狀態**：GitHub（開著的 issue、進行中 PR、最近 merge）。

註冊表每條來源記錄：取得方式（API／爬取／人工轉貼）、更新頻率、目前狀態（`active` / `planned` / `unavailable`）。設計要點：

- **質化訊號是一等公民**：評論與回報直接驅動兩條路 —— 明確的 bug/抱怨 → 開修復 issue（🟢）；重複出現的願望與痛點 → 形成假設卡的輸入。日報需含質化摘要（今日評論情緒、新回報議題）。
- **來源缺口比照數據缺口處理**：某類訊號沒有管道（例如遊戲內沒有回報功能、沒有社群空間）→ 標準動作是開「建立回報管道」issue 或向人類提案建立社群空間（🟡，屬對外內容），並在註冊表標 `planned`。
- **逐來源擴充**：新來源（新論壇、新社群）由人類或 bot 提議加入註冊表；未來新產品沿用同一張表的結構。

Phase 1 起步的 `active` 來源：商店數據、商店評論、GitHub 狀態；其餘依上述缺口流程逐步補齊。

## 數據觀測標準流程（數據缺口偵測）

這是 PM bot 的內建標準環節，對所有現在與未來的產品一體適用，不是冷啟動特例：

- 每張假設卡、每個決策**必須宣告驗證指標**（「用什麼數據判斷成功」）。
- Decide 步驟中，若所需指標**目前不可觀測** → 標準動作是開「建立數據管道」issue（埋點、接分析 SDK、建報表 API 等）餵進現有開發 pipeline，該假設卡標記 `blocked-on-instrumentation`。
- 新產品第一天沒有任何數據時，此迴圈自然先產出埋點 issue，無需特例規則。
- 在指標到位前，相關判斷以現有可得數據為準，且門檻檔明確標注「待接入」，不用不完整數據做重大判斷。

目前狀態：遊戲未接任何分析 SDK，起步僅有註冊表中標 `active` 的商店數據、商店評論與 GitHub 狀態。留存、DAU、遊戲內事件、回報管道等將由本標準流程驅動補齊。

## 記憶與狀態：產品日誌 repo（獨立 repo）

PM bot 的跨日連續性全部外部化到一個**獨立 git repo**（不放遊戲 repo 內：權限乾淨、bot commit 不污染遊戲 history）。PM bot 有讀寫權限。

```
product-journal/
├── PRODUCT.md              # 產品定位、目標受眾、當前策略方向（人類+bot 共同維護）
├── METRICS_BASELINE.md     # 健康度基準線與成長/終止門檻
├── SOURCES.md              # 訊號來源註冊表（量化數據/質化回饋/開發狀態）
├── metrics/
│   └── YYYY-MM-DD.json     # 每日指標快照（Collect 步驟原始輸出）
├── journal/
│   └── YYYY-MM-DD.md       # 每日日誌：分析結論、行動、理由
├── hypotheses/
│   └── H-NNN-<slug>.md     # 假設卡：假設→驗證指標→對應 issue→結果
└── decisions/
    └── D-NNN-<slug>.md     # 重大決策紀錄（提案→人類批准→執行）
```

- **假設卡是成長迴圈的核心單位**：PM bot 開的每個 issue 必須掛在一張假設卡上（「加入每日獎勵 → 預期 D7 留存 +2%」），發佈後回頭驗證、結果寫回卡片。成長成為可累積的實驗紀錄。
- **趨勢分析用歷史 JSON 快照計算**，不依賴 LLM 記憶。
- **人類可直接編輯** PRODUCT.md 與門檻檔以指導方向 —— Discord 之外的第二控制通道。

## 決策權限與護欄

三級權限，寫入 PM bot system prompt，並記錄在產品日誌供人類查閱修改。

### 🟢 自主執行（做完在日報揭露）
- 開 GitHub issue、調整 issue 優先序/標籤、關閉自己開的過時 issue
- mention 需求分析 bot 啟動 pipeline
- 更新產品日誌（快照、假設卡、日誌）
- 產出分析報告、競品研究（Phase 2+）

### 🟡 提案後執行（Discord 提案 → 人類明確同意才動）
- 方向性變更（改 PRODUCT.md 策略段落）
- 一次開超過每日配額的 issue
- 建議 merge / 建議發佈（Phase 3+）
- 任何對外內容：商店文案修改、社群公告草稿、行銷素材

### 🔴 只能建議、永遠不執行
- 終止產品（產出終止建議書，決定權在人類）
- 任何花錢的事（廣告投放、購買服務）
- 刪除性操作（關別人開的 issue、刪 journal 歷史）

### 護欄
- **每日 issue 配額**：預設每天最多 3 個新 issue（起始值，人類可在門檻檔調整）
- **pipeline 感知**：開新 issue 前檢查 pipeline —— 進行中 issue/PR 超過門檻（預設 5）就不餵新的，改在日報提醒「pipeline 塞住，等 merge」
- **提案逾時**：🟡 提案 48 小時無回應 → 不視為默許，改在日報持續追蹤，絕不自動升級為執行
- **異常煞車**：數據異常（崩潰率暴增、評分驟降）→ 暫停發想新功能，當日聚焦開修復 issue + 通知人類

## 成長／終止判斷框架

原則：**門檻由人類定，bot 誠實對照數據**，避免 LLM 憑感覺樂觀或悲觀。

`METRICS_BASELINE.md` 定義三層指標（初始值在 Phase 1 上線時由人類與 bot 用實際數據共同訂定）：

- **生命線指標**（活著的底線）：如 DAU、崩潰率、評分。跌破紅線 → 觸發異常煞車。
- **成長指標**（值得繼續投入的證據）：如 D1/D7 留存、下載趨勢、付費轉換。假設卡驗證的主要對象。
- **終止條件**（預先承諾的退出準則）：如「連續 3 個月 DAU 下滑且近 5 個實驗假設全部未達標」→ 必須產出終止建議書。

節奏三層，避免為每日雜訊做重大判斷：

1. **每日**：日報只陳述數據與短期趨勢，不做生死判斷。
2. **每週**：週報結算假設驗證 —— 哪些實驗成功/失敗、學到什麼、下週方向。
3. **每月**：健康度總評，輸出四擋之一：`健康成長` / `持平觀察` / `衰退警戒` / `建議終止評估`。後兩擋在 Discord 明確 @ 人類。

**終止建議書**（🔴 級輸出）必須包含：數據論證、已嘗試假設清單與結果、剩餘選項及不建議的理由、終止方式選項（下架／停更維持／開源／出售）。bot 的職責是備齊決策材料，讓人類做知情決定。

**防呆**：預先承諾的終止條件對抗沉沒成本謬誤；反之，條件未觸發時 bot 不得反覆嘮叨建議終止，月評未達警戒線就專注成長。

## 錯誤處理與可觀測性

- **API 拉取失敗**：某來源失敗 → 當日快照標注 `partial`，日報明講（含狀態碼與可能原因），分析只用拿得到的部分，**絕不腦補缺失數據**。
- **連續失敗**：同一來源連續 3 天失敗 → Discord @ 人類。
- **cron 心跳**：日報本身即心跳 —— 沒看到日報就知道掛了；journal repo commit 紀錄可查最後成功時間。
- **判斷可回溯**：每日行動必附理由與數據引用（哪個指標、哪天快照）；假設卡驗證結果不可刪改、只能追加。
- **憑證管理**：商店 API 金鑰走環境變數注入 openab 容器，絕不進 journal repo 或 prompt。

## 分階段路線圖

每個 Phase 獨立可上線、可驗證：

### Phase 1 — 感知與發想（本設計的實作範圍）
- PM bot 部署到 openab，usercron 每日循環
- 商店數據蒐集 → 分析 → 開 issue（🟢）→ 日報；數據缺口偵測驅動埋點 issue
- 產品日誌 repo、假設卡機制、週報/月評
- **成功標準**：連續兩週，(a) 日報有價值 —— 人類覺得「有它我更了解產品」；(b) PM bot 開出的 issue 至少一半被人類認可進入開發。

### Phase 2 — 成長工具箱擴充
- 競品與市場研究（web search）、玩家評論深度分析與回覆草稿
- ASO 建議（商店文案、關鍵字）、社群公告草稿（🟡）
- 前提：Phase 1 判斷品質已被信任。

### Phase 3 — 接手 merge 與測試
- 調度測試 bot（可能需新 bot：自動化測試、建 build）
- 測試通過 + 低風險變更 → 提案 merge（🟡，人類一鍵同意）
- 測試自動化是獨立子系統，屆時另行 brainstorming。

### Phase 4 — 接手發佈
- Play Console / App Store Connect 發佈自動化（fastlane 等）
- 風險最高、放最後，屆時另行設計。

## 非目標（本設計明確不包含）

- 測試自動化與發佈自動化的細部設計（Phase 3/4 另案）
- 具體門檻數值（Phase 1 上線時訂定）
- openab 本身的功能修改
- 廣告投放等付費成長手段的執行（永遠 🔴）
